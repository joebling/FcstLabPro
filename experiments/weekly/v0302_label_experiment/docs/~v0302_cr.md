## 一、Critical Bugs

### 🔴 C1: `generate_label_dip_recovery()` 的 recovery 用了“过去”的最低点，而不是“未来”的

**位置**: `label_factory.py` 第 66-76 行

**问题代码**:
```python
# ✅ dip: 正确地用了未来 T 天的最低点
future_min = df['close'].shift(-T).rolling(T).min()
dip = (future_min - df['close']) / df['close']

# ❌ recovery: 用的是过去 T 天的最低点！
rolling_min = df['close'].rolling(T).min()       # ← 这是 PAST 的低点
future_close = df['close'].shift(-T)
recovery = (future_close - rolling_min) / rolling_min  # ← 未来收盘价 vs 过去低点
```

**计划中的实现**（v0302_refactor_plan.md 第三节 Phase 1）：
```python
# 计划中 dip 和 recovery 都用同一个 "future minimum"
future_low = df['low'].rolling(21).min().shift(-21)  # 未来的最低点

dip = (future_low - df['close']) / df['close']
recovery = (df['close'].shift(-21) - future_low) / future_low  # 未来收盘 vs 未来低点
```

**⚠️ 注意：计划代码本身也有问题！**

`df['low'].rolling(21).min().shift(-21)` 这个写法是**错误的**：
- `rolling(21)` 是向后看的窗口（包含当前行及之前的 20 行）
- `.shift(-21)` 只是把结果整体向后移动 21 行
- 这**不是**"未来 21 天的最低点"

正确的写法应该是：
```python
# 方法 1: shift + rolling（推荐）
future_low = df['low'].shift(-1).rolling(T, min_periods=1).min()  # 从明天开始，未来 T 天的最低点

# 方法 2: 使用 shift(-T) 配合 rolling forward
future_low = df['low'].shift(-T).rolling(T, min_periods=1).min().shift(-(T-1))
```

**差异**:
- 实现中 `recovery` = 未来收盘价 / **过去**低点 — 计算的是“相对于过去的低点涨了多少”
- 计划中 `recovery` = 未来收盘价 / **未来**低点 — 计算的是“跌到底之后反弹了多少”

**语义差异巨大**:
- 在牛市中，“过去低点”可能在很久以前，`recovery` 会被人为抬高
- 模型学到的不是“跌后反弹”，而是“未来价格比过去低点高” — 在上升趋势中这几乎永远为真

**正确的修复方案**:
```python
def generate_label_dip_recovery(
    df: pd.DataFrame,
    T: int = 21,
    dip_threshold: float = 0.05,
    recovery_threshold: float = 0.03
) -> pd.Series:
    """
    B: Dip + Recovery (正确实现)
    
    Label = 1 if (未来 T 天先跌 > dip_threshold) AND (从低点反弹 > recovery_threshold)
    """
    # 未来 T 天内的最低价（从明天开始看）
    future_low = df['low'].shift(-1).rolling(T, min_periods=1).min()
    
    # dip: 未来最低点相对当前价格的跌幅
    dip = (future_low - df['close']) / df['close']
    
    # recovery: 未来收盘价相对未来最低点的反弹
    future_close = df['close'].shift(-T)
    recovery = (future_close - future_low) / future_low
    
    # Label: 先跌够阈值，再反弹够阈值
    label = ((dip < -dip_threshold) & (recovery > recovery_threshold)).astype(int)
    
    return label
```

**影响**: dip_recovery 的 IC=0.3406 不可信，模型可能学到的是"趋势"而不是"反转"

**严重性**: ⛔ 致命

### 🔴 C2: Sharpe 计算完全错误 — 预测与价格未对齐

**位置**: `run_label_comparison.py` 的 `calc_sharpe()` + 调用处

**问题链条**:

1. Walk-forward 产生 OOS 预测，每次 oos_window=63 天，step=21 天
   → 相邻 OOS 窗口有 42/63 = **67% 重叠**
   → predictions 中有大量重复预测（同一天可能被预测 3 次）

2. 调用方式：
   ```python
   sharpe = calc_sharpe(predictions, true_labels, close_prices,
                        list(range(len(X_valid))))  # ← 索引是 0,1,2,...,N
   ```

3. `aligned_prices = close_prices[0], close_prices[1], ...` 是原始日线价格（~2000 个）
   但 `predictions` 有 ~3500 个元素（因为 OOS 重叠）

4. 结果：`positions[i] * (close_prices[i+1] - close_prices[i])/close_prices[i]`
   其中 positions[500] 对应的不是第 500 天的预测，而是某个 OOS 窗口的第 N 个预测

**本质问题**: 预测序列和价格序列长度不同、索引不对应、日期不匹配。

**Sharpe 结果 (0.17, 0.11, -0.08) 全部无意义。**

**严重性**: ⛔ 致命

**正确做法**:
```python
# 方案 A: 记录每个预测的原始索引
def run_walk_forward(...):
    ...
    valid_indices.extend(range(t, t+oos_window))  # 已有但未正确使用
    ...

# 方案 B: 去重叠后再回测
# 对每个日期，只保留最新的预测（或平均）
# 然后按日期与价格对齐
```

## 二、Major Issues

### 🟠 M1: IC t-stat 计算方法学可疑

**位置**: `run_label_comparison.py` 的 `calc_ic_tstat()`

**问题**:
```python
def calc_ic_tstat(predictions, labels, step=21):
    n_no = n // step   # 先做 non-overlapping
    preds_no = predictions[:n_no*step:step]  # 得到 ~171 个样本

    for i in range(n_no):  # 再分组，每组 step=21 个
        p = preds_no[i*step:(i+1)*step]  # 每组 21 个 non-overlap 样本
        l = labels_no[i*step:(i+1)*step]
        ic = spearmanr(p, l)  # 组内 IC
        ics.append(ic)

    t_stat = ttest_1samp(ics, 0)  # 对 ~8 个 IC 做 t-test
```

**问题分析**:
1. `preds_no` 有 ~171 个元素（每 21 个取 1）
2. 然后再按每 21 个分组 → 得到 171/21 ≈ **8 个组**
3. 每组 21 个 non-overlap 样本，跨越 ~441 天 (近 2 年)
4. 在 2 年跨度内算 Spearman IC，多个市场周期混合

**这不是标准的 IC t-stat 计算方法。**

标准做法是：
- 对每个 OOS fold 计算一个 IC
- 或对每个日历月计算一个 IC
- 然后对 IC 序列做 t-test

**影响**: t-stat (4.97, 4.32, 3.19) 的绝对值不可靠，但**相对排序**（simple > excess > dip_recovery）在相同方法下可能仍然有参考价值。

**严重性**: 🟠 Major

### 🟠 M2: IC 计算的是 prediction vs label，而不是 prediction vs return

**位置**: `calc_non_overlap_ic()` 和 `calc_ic_tstat()`

**问题**:
```python
ic, p_val = spearmanr(preds_no, labels_no)  # preds vs 二分类 label
```

计划中的验收标准提到：
> "IC t-stat > 1.5" 和 "Sharpe > 0.3"

严格来说，金融中的 IC 通常指 `spearmanr(信号, 未来收益)`。
而这里算的是 `spearmanr(信号, 二分类 label)` — 更像是“分类精度”而不是“收益预测能力”。

**但是**: 对于 **label 对比实验**来说，使用 `pred vs label` 的 IC 也是合理的，
因为我们比较的是“模型对不同 label 的预测能力”。
只是不能直接跟 v0301 的 IC=0.65 比较（那个也是 vs label，但 label 定义不同）。

建议在报告中明确标注这是 **Classification IC**，不是 **Return IC**。

**严重性**: 🟠 Major（不是 Bug，但需要标注清楚）

## 八、补充说明

### 8.1 计划文档中的代码问题

在审查过程中发现，`plans/v0302_refactor_plan.md` 中的示例代码本身也存在问题：

```python
# 计划中的代码（错误）
future_low = df['low'].rolling(21).min().shift(-21)
```

**问题分析**：
- `rolling(21)` 是向后看的窗口（包含当前行及之前的 20 行）
- `.shift(-21)` 只是把 rolling 结果整体向后移动 21 行
- 这**不是**"未来 21 天的最低点"，而是"21 天前的过去 21 天最低点"

**正确理解 pandas rolling**：
| 操作 | 含义 |
|------|------|
| `df['low'].rolling(21).min()` | 当前行及之前 20 行的最低点（向后看） |
| `df['low'].shift(-1).rolling(21).min()` | 从下一行开始，未来 21 行的最低点（向前看） |

**教训**：在编写时间序列代码时，务必仔细验证 rolling 和 shift 的组合语义，最好用小数据集手动验证。
